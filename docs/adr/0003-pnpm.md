# ADR 0003 — pnpm 10 en vez de npm workspaces

- **Estado:** Aceptada
- **Fecha:** 2026-09-04
- **Contexto:** POC `pokedex-vuejs`, base técnica del microfrontend de PeopleFirst
- **Relacionadas:** [ADR 0001](0001-module-federation-en-monorepo.md),
  [ADR 0002](0002-turborepo.md), [Registro de riesgos](../riesgos.md)

---

## Contexto

Tres cosas empujaban esta decisión:

1. La planificación de PeopleFirst pide **pnpm 10**; la POC usaba npm workspaces. Divergencia
   abierta (riesgo R22).
2. El repo tenía **dos lockfiles** conviviendo — `package-lock.json` (el que se usaba) y un
   `pnpm-lock.yaml` residual de 5,8 kB. Detección ambigua de gestor de paquetes (riesgo R11).
3. La hipótesis de que el `node_modules` plano de npm estaba escondiendo problemas.

El punto 3 era el interesante, y **la hipótesis que yo tenía era incorrecta**. Vale la pena
dejarla escrita porque el error es instructivo.

## La hipótesis equivocada, y qué es verdad

> **Lo que afirmé antes de medir:** "pnpm mata el riesgo R8 porque su `node_modules` no es
> plano, así que los fallos de singleton dejan de esconderse en dev."

**Eso es falso.** La ilusión del dev server no viene principalmente del hoisting. Viene de
que un dev server sirve módulos sin minificar y sin chunkear: cada app corre su propio Vite
en su propio origen, y las tres declaran el mismo rango semver, así que resuelven versiones
compatibles con cualquier gestor de paquetes. Cambiar de npm a pnpm **no** hace que el
contrato `shared` se ejercite en dev.

Lo que sí es verdad, y es medible, resultó ser algo distinto y más incómodo:

> **El grafo de chunks federados cambia según el gestor de paquetes.** El artefacto que
> testeás con un install hoisted no es estructuralmente el mismo que desplegarías con un
> install estricto.

### La medición

Mismo commit del código de aplicación, misma versión de `@module-federation/vite`, mismo
`sharedSingletons`. Solo cambia el gestor de paquetes. Chunks de fallback emitidos en
`apps/remote-pokemon/dist/assets/`:

**Con npm (hoisted) — 2 chunks, fundidos:**

```
151,0 kB  …__loadShare___mf_0_pinia_mf_1_colada__loadShare__.js
 28,8 kB  …__loadShare__vue_mf_2_router__loadShare__.js
          (vue NO tiene chunk propio)
```

**Con pnpm (estricto) — 4 chunks de fallback + 4 shims, uno por dependencia:**

```
117,9 kB  …__prebuild__vue__prebuild__.js
 26,2 kB  …__prebuild__vue_mf_2_router__prebuild__.js
 15,2 kB  …__prebuild___mf_0_pinia_mf_1_colada__prebuild__.js
  8,2 kB  …__prebuild__pinia__prebuild__.js
  5,6 kB  …__loadShare__vue__loadShare__.js
  3,0 kB  …__loadShare__vue_mf_2_router__loadShare__.js
  3,0 kB  …__loadShare___mf_0_pinia_mf_1_colada__loadShare__.js
  2,8 kB  …__loadShare__pinia__loadShare__.js
```

`dist/` total por remote: **508 kB (npm) → 532 kB (pnpm)**, +24 kB (+4,7 %).

### Cómo lo leo

Bajo npm, el chunk de 151 kB etiquetado como el share de `@pinia/colada` es
aproximadamente la suma de vue (117,9) + colada (15,2) + pinia (8,2) = 141,3 kB. La lectura
razonable es que **el fallback de Vue quedó fundido dentro del chunk de colada**, porque con
todo hoisted a la misma ruta física el bundler no separó los grafos. Es inferencia a partir
de los tamaños y los nombres, no certeza — no desarmé los bundles.

Las dos consecuencias, si la lectura es correcta:

1. **Granularidad de la negociación.** Si el host provee Vue pero la negociación falla solo
   para colada, el build de npm tiene que bajar un chunk de 151 kB que contiene las tres
   librerías; el de pnpm baja los 15 kB de colada. El fallback deja de ser por dependencia.
2. **Y la que importa más:** el artefacto verificado en CI con npm no tiene la misma
   estructura que el que se desplegaría con pnpm. Es una versión más fuerte de "verificar
   contra builds, no contra dev servers": también hay que verificar contra el **mismo
   install** que produce el artefacto de producción.

+24 kB por remote es más grande, sí. Pero es más grande **por ser correcto**: el chunk
fundido era más chico solo por ser un blob único.

## Lo que pnpm encontró, y lo que no

**No encontró dependencias fantasma: cero.** Las tres apps declaran correctamente lo que
importan, así que el install estricto pasó de primera. Es un dato a favor de la POC, y hay
que decirlo: el beneficio más publicitado de pnpm acá **no aplicó**. En un codebase menos
disciplinado sería distinto — y ese es exactamente el escenario del monolito de PeopleFirst.

Sí destapó dos cosas reales:

1. **`npm-run-all2` estaba declarado en las tres apps y no lo usaba ningún script**
   (quedó sin uso al simplificar `build` y `lint` en el ADR 0002). npm nunca se quejó.
2. **pnpm 10 bloquea los scripts de `postinstall` por defecto.** `unrs-resolver` —el binario
   nativo de `eslint-import-resolver-typescript`— necesitó permiso explícito vía
   `onlyBuiltDependencies` en `pnpm-workspace.yaml`. Bajo npm, cualquier dependencia
   transitiva podía ejecutar código arbitrario en el install sin que nadie lo aprobara.
   Esto es una mejora de postura de seguridad, y es la clase de cosa que un install estricto
   te obliga a mirar.

## Decisión

**pnpm 10** como gestor de paquetes, con `packageManager` fijado en el `package.json` raíz.

```yaml
# pnpm-workspace.yaml — reemplaza el campo `workspaces` del package.json
packages:
  - 'apps/*'
  - 'packages/*'

onlyBuiltDependencies:
  - unrs-resolver
```

Cambios asociados:

- `package-lock.json` eliminado; `pnpm-lock.yaml` es el único lockfile. **Resuelve R11.**
- El link al workspace pasa a ser explícito: `"@pokedex/mf-shared": "workspace:*"` en las
  tres apps, en vez de `"*"`. Falla ruidosamente si el paquete desaparece, en vez de irse a
  buscarlo al registry.
- `npm run <script> --workspace <app>` → `pnpm --filter <app> run <script>` en
  `playwright.config.ts` y `lint-staged.config.js`.
- CI: `pnpm/action-setup@v4`, `cache: pnpm` y `pnpm install --frozen-lockfile`.
- `npm-run-all2` fuera de las tres apps.

### El beneficio concreto que sí se cobra hoy: el Dockerfile

Bajo npm workspaces, el build del host tenía que instalar el árbol completo:

```dockerfile
RUN npm ci --workspace host --include-workspace-root   # instala TODO
```

Con pnpm, el subgrafo es expresable:

```dockerfile
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/host/package.json apps/host/
COPY packages/mf-shared/package.json packages/mf-shared/
RUN corepack enable && pnpm install --frozen-lockfile --filter host...
```

`--filter host...` (con los tres puntos) instala el host **y sus dependencias de
workspace**, nada más. Mejora directa del riesgo **R7**: el acoplamiento de instalación
entre apps baja de "todo el árbol" a "el subgrafo real".

## Consecuencias

### A favor

- Un solo lockfile, sin ambigüedad de gestor (**R11 resuelto**).
- Install del subgrafo por app en Docker y CI (**R7 mejorado**).
- El grafo de chunks federados queda separado por dependencia, que es lo que MF pretende.
- `postinstall` bloqueado por defecto: las dependencias que ejecutan código en el install
  son una lista revisable, no un hecho invisible.
- Install: 8,7 s en frío, 1,2 s tibio.
- Alineado con lo que pide la planificación de PeopleFirst (**R22 cerrado en este punto**).
- `--filter` nativo, que compone bien con el `--filter` de Turborepo.

### En contra

- **Todo el equipo necesita pnpm.** Mitigado por `packageManager` + `corepack enable`, pero
  es un paso de onboarding más y un cambio en la memoria muscular de todos.
- **+24 kB por remote** en el `dist/`.
- **La resolución estricta puede romper paquetes que dependen del hoisting.** Acá no pasó,
  pero es el riesgo principal de esta migración en un codebase más grande. Escotilla:
  `node-linker=hoisted` devuelve el comportamiento de npm — y anula el beneficio, así que
  usarla es admitir que la migración no se completó.
- CI necesita un paso más (`pnpm/action-setup`).

### Lo que esta decisión NO resuelve

- **No arregla R8.** El E2E contra builds (`pnpm test:e2e:preview`) sigue siendo la única
  verificación real de la composición federada. Si algo, la medición de arriba lo vuelve
  _más_ importante: ahora sabemos que el artefacto depende también del install.
- **No arregla R6** (URL de los remotes horneada en el build del host). Eso va en su propia
  rama, `feat/runtime-remotes`.

## Verificación

```
$ turbo run lint type-check test build
 Tasks:    14 successful, 14 total

$ turbo run //#smoke
 ✓ 27 comprobaciones — contrato ./routes expuesto, los 4 singletons con
   singleton: true y el requiredVersion del contrato, CORS y Cache-Control
```

**Hueco de verificación declarado:** el E2E con Playwright (`pnpm test:e2e:preview`) **no se
corrió** en esta migración — el entorno donde se preparó no tiene navegador ni permisos para
instalar las librerías de sistema que Chromium necesita. Es la verificación que más importa
y está pendiente.

Para cubrirlo parcialmente sin navegador se agregó `scripts/smoke-federation.mjs`, que
verifica la coherencia de los artefactos: cada `remoteEntry.js` y `mf-manifest.json`
responde, el contrato `./routes` está expuesto, los cuatro singletons vienen con
`singleton: true` y el `requiredVersion` del contrato, y los headers de CORS y
`Cache-Control` son los correctos. Apuntado a las URLs del bucket en vez de a localhost, es
también el smoke test post-deploy que pide el riesgo **R17**.

**Antes de mergear esta rama, correr:**

```bash
pnpm install
pnpm --filter host exec playwright install --with-deps chromium
pnpm test:e2e:preview          # ← los 12 E2E contra los builds. Es el que decide.
```

Si esos 12 pasan con pnpm, la migración está verificada de punta a punta. Si alguno falla,
el fallo es información valiosa: significa que el cambio de grafo de chunks documentado
arriba tiene un efecto observable en runtime, y hay que entenderlo antes de mergear.

## Alternativas consideradas

| Alternativa                        | Evaluación                                                                                                                                                                                                            |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Quedarse en npm workspaces**     | Deja R11 abierto, mantiene la divergencia con la planificación (R22) y no permite instalar el subgrafo en Docker. Funciona, pero no cierra nada.                                                                      |
| **Yarn (Berry, PnP)**              | Más estricto todavía, y ahí sí romperían cosas: PnP no crea `node_modules` y varias herramientas del stack (oxlint, vue-tsc, el plugin de MF) asumen resolución de Node clásica. Costo de migración desproporcionado. |
| **Bun**                            | Install muy rápido, pero es una pieza menos probada en este stack (MF + Vite + Vitest + Playwright) y la planificación de PeopleFirst no lo pide.                                                                     |
| **pnpm con `node-linker=hoisted`** | Instala con pnpm pero reproduce el `node_modules` plano de npm. Anula el motivo de migrar. Solo tiene sentido como escotilla temporal si algo rompe.                                                                  |
